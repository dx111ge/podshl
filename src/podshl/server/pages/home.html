Why this exists

Support knowledge fails in four ways at once, and none of them is fixed by writing more of it.

1. The knowledge is not in the tickets

We measured 20,321 resolved German helpdesk tickets, looking for the thing everyone assumes is in there: the repair step.

2. Written instructions rot, because they describe a path

An article says "click Start → Settings → System → Display → Advanced". After the next OS update it is wrong. That is not an edge case, it is the steady state — and the cause is structural: an article describes a path, but what it means is an intent.

3. And nobody knows what is on the machine

This is the largest one. Today it is answered by asking the user to run dxdiag or paste journalctl output, over a multi-day round trip, and answered wrong. Half of all failures are the person not being in the situation the article assumes — and static text cannot notice that.

4. And now the evidence is disappearing

Something changed in the last few years, and it works against open source specifically. A user who got stuck used to file an issue. Now they ask an assistant, get unstuck in ninety seconds, and close the tab. The problem was real, it happened to hundreds of people, and the maintainer never hears about a single one of them.

And the signal is sharper than an issue report ever was. Every report says which size of model was involved. A small model running on somebody's own laptop, solving a problem out of public knowledge, means the answer was already out there and your product simply failed to convey it. That is a documentation or interface defect, precisely located — not a knowledge gap, and not something you would ever have learned from silence.

Open source is where this bites hardest, because it runs on the willingness of people to report things. Nothing is shown below five distinct reporters, so what reaches a maintainer is a pattern rather than an anecdote — and it arrives without anybody having to write a paragraph, wait for a triage, or be told their report is a duplicate.

Why it is safe to let this near a machine

A publisher may only choose, never invent

The list of what can be read, and the list of what can be changed, both live in the client. A publisher names an operation and fills in declared parameters. A careless or compromised one can mis-parameterise something tested — validation and the dry run catch that — but cannot introduce a capability. Extending either list is a client release people choose to install.

Nothing happens without being shown

  • Read, transmit and change are three separate consents.
  • The refusing button holds focus, so a stray Return never grants.
  • Whatever is withheld becomes a question, not a dead end.
  • Every change is dry-run first, and reversible.

Unknown is not untrusted. A project that publishes a perfectly good agent without ever hearing of us still works. Anything else would make this a chokepoint rather than a participant — and a project absent from our list has done nothing wrong.
